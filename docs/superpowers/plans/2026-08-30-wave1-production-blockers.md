# Wave 1 — production blockers from the dossier/order workflow audit

Spec: `docs/delivery/dossier-order-workflow-audit.md` (findings C-01, C-02, C-03, C-04, H-06, H-14). The audit is the binding authority for *what* is wrong; the recommended solutions there are suggestions, not mandates.

## Global constraints (binding for every task)

- Backend invariants must not depend on frontend restrictions; every guard is server-side and covered by an adversarial service/API test.
- Preserve tenant isolation (`TenantScoped()` / global filter) and `[RequirePermission]` on every endpoint; never widen a permission.
- Preserve finalized financial snapshots (invoice `*Snapshot` fields, pricing snapshot `Locked/Invoiced`).
- Preserve existing stop/package/execution/POD/label/ETA references where an order edit does not logically replace a stop.
- Do not weaken auditability: every mutation keeps (or gains) its `IAuditService.RecordAsync` entry with old→new where it existed.
- No new parallel domain concepts (no second "customer" field, no second status enum, no duplicate time model).
- Avoid schema changes unless genuinely required; a migration must be additive and safe for existing production rows (defaults, no data loss).
- TDD: write the failing regression test first, then the fix. Run the covering test files after each change; run the full suites before reporting.
- Dutch user-facing messages, consistent with neighbouring messages in the same service.
- Do not touch files outside your task's file list without recording why in your report.
- Commit on your worktree branch with clear messages; do not push.

### 1b — C-02

Keep create-time behaviour unchanged. Also add `CustomerId` to `PricingInputsChangedAsync` only if a path still exists that can change it (after the guard, none should — verify and state so). FE: disable the customer/entity selects when editing an existing order and show the existing "Klant wijzigen…" / "Entiteit wijzigen…" affordances (they exist on the detail page). ### 1c — C-01
`UpdateAsync` removes all stops and rebuilds them with new ids (`:726-741`, `BuildStops:1640-1643`). Soft delete keeps the old rows, so `Package.LoadingStopId/DeliveryStopId`, `StopExecution`, `ProofOfDelivery`, `ScanEvent`, `StopEta`, `ExecutionException` keep pointing at hidden stops; `PackageLabelService`, `PackageScanProcessor`, `ScanService`, `TransportOrderTimelineService` all resolve through the filter.
Required analysis before coding: define stop identity. Proposal to validate against the code: a client stop that echoes an existing `Id` belonging to this order **is the same stop** (update in place: sequence, type, location, address fields, windows, requirements, instructions, snapshot carry-over/refresh rules exactly as today); a stop without an `Id` (or with an unknown id) is **new**; an existing stop not echoed is **removed** (soft-deleted). Removing a stop that has packages pinned to it, executions, POD, or scan events must be **refused** with a clear message (the order is Confirmed and physically bound) unless the order is Draft/Submitted. Changing a stop's `StopType` is a replacement in identity terms — decide and document (recommended: refuse type change on a stop with references; allow otherwise). Cargo relinking (`RelinkCargoToReplacedStops`) must keep working for new stops and become a no-op for preserved ones. Sequence renumbering must not create phantom rows. `Version` bump and audit (`StopSnapshotRefreshed`, `Updated` StopRequirements summary) unchanged.
Tests: confirm order with cargo → packages generated (use `PackageGenerationService`) → `UpdateAsync` echoing stop ids with changed instructions → same stop ids, package pins unchanged and resolvable through the filtered set, `StopExecution` rows (seed one) still resolve; add a stop → new id only for the new one; remove an unreferenced stop → soft-deleted, others intact; remove a stop with packages on a Confirmed order → 400; client sending a stop id of **another order/tenant** → treated as new (not adopted), test it; `PackageLabelService` snapshot after edit still has addresses (if a label test harness exists; otherwise assert the resolved stop). Existing tests that asserted "stops get new ids" must be updated to the new invariant with a comment.

## Task 2 — H-06 (invoicing/financial integrity)

Files: `Modules/Invoicing/**` (service, controller, DTOs), `Modules/Peppol/**` read-only, `TransportationService.Api.Tests/Invoicing/**`, `TransportationService.Web/src/features/invoices/**` (hide/relabel the cancel action; cosmetic).

Facts: `InvoiceService.Transitions[Sent] = [Paid, Cancelled]` (`:27`); `ChangeStatusAsync` (`:768-880`) has no guard; `ReleaseOrdersAsync` (`:1056-1101`) returns orders to Completed and pricing snapshots to Locked; `CancelQueuedPeppolTransmissionsAsync` (`:1034-1041`) only cancels Queued; `DeleteAsync` (`:904`) deletes Cancelled invoices; `CreateCreditNoteAsync` (`:1279-1320`) exists (Sent/Paid, one live credit note per invoice, full copy); credit-note lines copy code/category/rate only and Send re-runs `FreezeLedgerSnapshotsAsync`/`FreezeSalesCodeSnapshotsAsync` for every kind (`:846-865`); `CreateAsync` has no `Distinct()` on order ids (`:239-248`); `ChangeLegalEntityAsync` in `TransportOrderService` (`:464-472`) releases draft lines but leaves `pricingSnapshot.Status = Invoiced`.
Invariant to enforce: once an invoice has been finalized (status `Sent` or `Paid`, or any Peppol transmission beyond `Queued`), its orders can never become billable again through cancellation; correction goes through the credit note. Minimal robust fix: (1) `Sent → Cancelled` is refused when the invoice has been finalized — define "finalized" from the existing model (Sent/Paid status; and/or a transmission with status ≥ `SubmittedToProvider`); return the credit-note hint used elsewhere (`:538-546`). If a legitimate "cancel a Sent invoice that was never transmitted/printed" case must remain, it must **not** release the orders (they stay `Invoiced`) — decide, document, test. (2) Credit notes: copy all `*Snapshot` fields from the credited lines and skip both Freeze methods for `Kind == CreditNote` so the credit reflects the original fiscal data. (3) `CreateAsync`: `Distinct()` + refuse duplicates. (4) Keep `DeleteAsync` from deleting a Sent-derived Cancelled invoice if any such rows can exist. (5) Do not change credit-note↔order release semantics beyond what is needed (P-05 is Wave 2), but verify the credit-note flow still works end-to-end and is tested. FE: hide "Annuleren" for Sent/Paid invoices and show "Creditnota aanmaken" (already exists).
Tests: Sent invoice → cancel → refused, orders still `Invoiced`, snapshot still `Invoiced`; Sent with Delivered transmission → refused; Draft → cancel still works and releases; credit note from Sent invoice keeps snapshots after a sales-code remap; duplicate order ids → Invalid; Paid → cancel refused; existing invoice tests green.

## Task 3 — C-03 (frontend/time handling, one transport-time convention)

Files: `TransportationService.Web/src/utils/dates.ts` (+ tests), `src/features/transport-orders/components/sections/orderFormPayload.ts`, `orderFormState.ts`, `StopExecutionPlanDialog.tsx`, `pages/TransportOrderDetailPage.tsx` (time rendering only), `src/features/dossiers/components/DossierRouteSummary.tsx`, `src/features/customer-portal/pages/CustomerPortalNewOrderPage.tsx` + `CustomerPortalOrderDetailPage.tsx` (time encoding/rendering only), the display-preferences provider that loads `GET /api/company-settings/display` (find it: grep `DisplayPreferences`), FE tests; backend: `Modules/Edi/Services/EdiService.cs` (stop time parsing + mapping to `RequestedFrom/To`) + its tests only. Do NOT change how the API stores or serialises timestamps.

Convention to establish (verify against code, then implement): backend stores stop windows as UTC instants (`timestamp with time zone`, Npgsql) and serialises ISO-8601 with `Z`. The **wire format is UTC**. Operational wall-clock times are entered and displayed in the **tenant time zone** (`TenantSettings.Timezone`, served by `GET /api/company-settings/display` as `timezone`, default `Europe/Amsterdam`), never the browser zone. Implement in `utils/dates.ts`: `setTimeZonePreference(tz)`, `getTimeZonePreference()`, `toWireDateTime(dateYYYYMMDD, timeHHmm) → ISO UTC` and `fromWireDateTime(iso) → { date, time }` using `Intl.DateTimeFormat` with `timeZone` (no library), plus `formatDateTime`/`formatTime` rendering in the tenant zone. Replace every `...:00Z` construction and every `slice(11,16)` on stop times with these helpers (form, execution-plan dialog, dossier route summary, portal new-order/detail). Load the timezone in the display-preferences provider alongside the date format. Portal: same helpers (portal customers are in the tenant's zone for operational times; note the deliberate i18n split for date *format* only).
Backend: `EdiService.MapStops` parses with `DateTimeStyles.AdjustToUniversal | DateTimeStyles.AssumeUniversal` (document that partner payloads must carry an offset or are UTC) and maps partner windows to `RequestedFrom/To`, not `PlannedFrom/To`; update EDI tests.
Planning/ETA backend comparisons (R2B-14) are out of scope for this task — record the verification in the report only.
Tests: unit tests with `TZ` independent assertions (`Intl` with explicit zone): 08:00 Europe/Amsterdam summer → `T06:00:00Z` and back; DST boundary day; round-trip create → GET → edit → GET without drift (form payload → DTO fixture → `stopsFromOrder` → payload equality); detail table renders 08:00 for `T06:00:00Z` in summer regardless of the machine zone (set `process.env.TZ` in the test to a different zone to prove browser-independence); dossier summary equals detail; EDI payload with offset → `RequestedFrom` set, `PlannedFrom` null.

## Task 5 — C-03 backend follow-ups + C-01 data repair (after Tasks 1 and 3 are merged)

Files: `Modules/Orders/Services/TransportOrderService.cs` (opening-hours warnings only), one data migration under `TransportationService.Api/Migrations`, `Modules/Tenancy` read-only (TenantSettings.Timezone), tests in `TransportationService.Api.Tests/Orders/**` (`StopOpeningHoursWarningTests.cs` and a migration/SQL test if the harness allows).

### 5a — Existing stop windows carry the old "wall clock stamped as UTC" encoding
Before Task 3 the web client sent `2026-08-30T08:00:00Z` for a wall-clock 08:00; the API stored it as 08:00 UTC. After Task 3 the client interprets that instant in the tenant zone (10:00 in summer). Existing rows in `transport_order_stops` (`PlannedFrom/To`, `RequestedFrom/To`, `ConfirmedFrom/To`, `EarliestAllowed/LatestAllowed`) must be re-encoded once: new = the stored naive wall clock interpreted in the tenant's `TenantSettings.Timezone` → UTC. In PostgreSQL: `col = ((col AT TIME ZONE 'UTC') AT TIME ZONE ts.timezone)` joined on `tenant_settings` by `TenantId` (verify table/column names from the model snapshot). Do NOT touch execution/POD/ETA/audit/status-history timestamps (server clock, already true UTC). Rows created by EDI carried a real offset and get shifted once — accept and document (low volume; list the count query). Make the migration idempotent-safe: guard with a marker (e.g. only run when a `TenantSettings` flag/`__EFMigrationsHistory` row proves it never ran — EF's history already guarantees single execution; state that). Provide a `Down` that reverses the expression. Write the SQL so it is a no-op for tenants whose timezone is `UTC`. Also decide about `dock_appointments`/other tables the web client wrote with the same `:00Z` pattern — grep the FE at fb7c0fb for other `:00Z` producers (`DockPlanningPage`, `AttendanceTab` were noted) and either include them with the same expression or document why not.

### 5b — `BuildOpeningHoursWarnings` compares raw UTC with local opening hours
`TransportOrderService.BuildOpeningHoursWarnings` (~`:1826-1872`) uses the UTC `TimeOfDay`/`DayOfWeek` of `PlannedFrom/To` against the location's local opening hours, and its date-only guard `TimeOfDay == TimeSpan.Zero` no longer matches after Task 3. Convert the instants to the tenant zone (`TimeZoneInfo.FindSystemTimeZoneById(settings.Timezone)`, with a safe fallback to UTC when the id is unknown) before comparing, and redefine "date-only" as local midnight in that zone. Load the tenant timezone once per call (tenant settings are already read elsewhere in the service — reuse the pattern). Update `StopOpeningHoursWarningTests.cs`: 08:00 local in summer (06:00Z) inside 07:00–17:00 hours → no warning; 06:00Z as a *UTC* reading would have been "before opening" — assert the new behaviour; date-only stop (local midnight) → no time warning; a tenant with `UTC` timezone keeps the old results.

### 5c — Feasibility of repairing pre-fix dangling stop pins (C-01 data)
Orders edited before Task 1 have packages/executions/PODs pointing at soft-deleted stops. Evaluate whether a deterministic repair is possible: for each soft-deleted stop with dependants, find the live stop of the same order with the same `StopType` and `Sequence` (and same `LocationId`/address when several) and re-point `Package.LoadingStopId/DeliveryStopId` (and only those — executions/POD/scans are historical facts and stay). If unambiguous, implement it as a second data migration with a count log; if ambiguous cases exist, leave them and write the diagnostic query into the report (Wave 2). Do not guess.

Tests for 5a/5b run on SQLite; the SQL migration itself cannot run there — cover the conversion expression with a small unit test on an equivalent C# function if you factor one, and document the manual PostgreSQL verification steps (run against the local Docker DB is NOT allowed in this task — describe, don't execute).
