# Business Feedback Wave — Implementation Plan (2026-07-21)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This plan is executed in-session by the authoring agent; interface contracts are specified exactly, step-level code is authored at implementation time following the conventions locked in §Architecture Decisions and the repo audit facts in §Audit Summary.

**Goal:** Implement the 27-phase business-feedback wave: multiple own legal entities with entity-scoped monthly invoice numbering, customer master-data expansion (numbering import, contacts, addresses, fiscal/Peppol/bank, communication rules, diesel surcharge, PO policy), invoice entity validation + attachments, HR expansion (employee fields, documents, reminders, issued items, driver merge), fleet compliance (Maut, documents upload, tachograph, leasing, KPI pages), managed order units and the package-label redesign.

**Architecture:** Modular monolith (controller → service → DbContext), hand-rolled services, `[RequirePermission]`, tenant scoping via explicit `TenantId` predicates, additive EF migrations, Dutch UI copy. All new capability extends existing aggregates (TenantSettings, Customer, Location, Invoice, Employee, Driver, Vehicle, Trailer, Package label pipeline) — no parallel domains, no duplicate numbering/document/notification systems.

**Tech Stack:** .NET 10, EF Core + Npgsql (tests: in-memory SQLite via `SqliteTestDbContext`), React 19 + react-router 7 + Vite 8 (no new runtime deps), PDFsharp 6.2.4 + QRCoder + hand-rolled `Code128Encoder` for labels, ClosedXML for import/export, xUnit + Vitest.

## Global Constraints

- No rewrites; reuse and extend existing models/services/validators/permissions/document infra/notifications/audit/migrations.
- Additive migrations only; never edit historical migrations; migrate old single fields into new collections preserving a primary/default value.
- Tenant scoping: new entities inherit `AuditableTenantEntity` (exception: none planned), explicit `TenantId` predicates, TenantId-first indexes, filtered unique indexes where uniqueness is soft-delete-scoped.
- Numbering: reuse `TenantNumbering.SaveWithClaimedNumberAsync` concurrency-token pattern; never reuse finalized invoice numbers.
- Permissions: constants in `PermissionCodes` + `All` catalog tuple (Dutch description), `[RequirePermission]` any-of, `DefaultRoleDefinitions` update + `DefaultRoleUpgrades` **v9** step.
- Audit via `IAuditService.RecordAsync` with purpose-built anonymous objects; never document contents/passwords/tokens.
- Files via `IFileStorageService` (`LocalFileStorageService`), upload endpoints copy the Qualifications controller pattern (`[RequestSizeLimit]`, extension + size validation, opaque storage keys).
- Frontend: existing design system (`src/components/ui`), `lazyPage` routes, colocated CSS, `SearchableSelect`/`LookupSelect` combobox patterns, Dutch copy, request-key fetch idiom, ProblemDetails via `describeApiError`.
- Verification gate after every phase: `dotnet build`, `dotnet test`, `npx tsc -b`, `npm run lint`, `npm test`, `npm run build`.
- Do not delete or weaken existing tests.

## Audit Summary (facts the plan builds on)

- **Own company today** = single `TenantSettings` row (`Modules/Tenancy/Entities/TenantSettings.cs`): company profile, addresses, contact, `Iban`, `DefaultCurrency`, `PaymentTermDays`, `DefaultVatRatePercent`, `LogoReference` (reference-only), and all `*NumberPrefix`/`*NumberNextValue` counters (concurrency tokens). No legal-entity concept, no company-side Peppol.
- **Invoice** (`Modules/Invoicing`): `InvoiceNumber` = `TenantSettings.InvoiceNumberPrefix + NextValue:0000` via `TenantNumbering`; statuses `Draft→Sent→Paid/Cancelled`; totals computed from lines; unique `(TenantId, InvoiceNumber)` filtered index; **no PDF, no sending, no attachments, no PO field, no entity link**.
- **Customer** (`Modules/Partners`): has `CustomerNumber` (`KL-` + counter, unique filtered index), inline registered address, `CustomerContact` (FirstName/LastName/Role/Email/Phone/IsPrimary/Notes), VAT profile (`VatTreatment` enum, `DefaultVatRatePercent`, `VatCountryCode`, `VatNotes`, `PeppolId`, `PeppolScheme`, `VatNumberValidator` BE mod-97), `InvoiceEmail`, `PaymentTermDays`, `InvoiceLanguageCode`, flags `PurchaseOrderRequired`/`CustomerReferenceRequired`/`SignedDeliveryNoteRequired`. **No bank fields, no currency, no nickname, no import.**
- **Addresses**: central `Location` entity with `CustomerId?`, `LocationType` enum (string-stored), `IsDefaultLoadingLocation`/`IsDefaultUnloadingLocation` filtered unique defaults, free-text `OpeningHours`, instructions, contact fields.
- **Rate cards** (`Modules/Tarification`): per-customer `RateCard` + `RateSurcharge (Percent|Fixed)` + quote engine. No diesel-surcharge index model.
- **Orders**: `TransportOrder.CustomerReference` doubles as PO; `QuantityUnit` free text on order + `CargoItem`; `CargoItem.UnitType : PackageUnitType?` enum + `UnitTypeLabel`; stops carry `LocationId?` or inline address + Planned/Requested/Confirmed windows.
- **Import/export**: ClosedXML; `PackageImportService` = template/preview/commit reference implementation (max 1000 rows, Dutch headers, error workbook base64, `allOrNothing`).
- **Employee** (`Modules/Employees`, NOT AuditableTenantEntity base — `ITenantOwned, IAuditableEntity`, no soft delete): person/contact/address, `NationalRegisterNumber`+`Iban`+`Bic` confidential (redacted without `employees.view_confidential`), single `EmergencyContactName/Phone`, `EmploymentStartDate/EndDate`, `EmploymentStatus`, multi `JobFunctions`. **No civil status, DIMONA, identity-card number, dependents.**
- **Driver** (`Modules/Drivers`): 1:1 `EmployeeId` (unique), `DriverNumber` `CH-####`, single `DriverCategoryId` (operational lookup), `AvailabilityStatus`, `IsBlocked/BlockReason`, `FixedTrailerId`; vehicle slots live on `Vehicle.FixedDriverId/CurrentDriverId` (SoT `FleetAssignmentService`). - **Qualifications**: `EmployeeQualification` (+`DocumentPath` upload via reference controller pattern, ≤10 MB pdf/jpg/jpeg/png), `QualificationType.RequiresExpiryDate`, `QualificationStatusCalculator`; `employee_documents.*` permission family already gates these.
- **Employee documents**: no dedicated entity — only qualification attachments + `Absence.AttachmentPath`.
- **Notifications**: `Notification` + `NotificationPreference` + `NotificationTypeCatalog`; `ExpiryNotificationHostedService` (6 h sweep) + `ExpiryNotificationProducer` (qualifications + fleet documents; dedupe = `#id` LinkPath fragment within 7-day window; horizon `TenantSettings.QualificationExpiryWarningDays`). Outbox: `Modules/Messaging` `OutboxMessage` (idempotency key unique/tenant), `MessageKinds`, `MessageTemplate`, `MessagingProfile`, `MessageDispatcher` (dev sink only), `OutboxDispatcherHostedService` (30 s).
- **Conflicts**: `PlanningConflictService` (categories, override metadata, tenant-configurable severities), persistent `ConflictOverride` (reason mandatory), `Modules/Eligibility` (`DriverEligibilityEvaluator` — licence rank B<C<CE, Code95, ADR, medical, crane; `EligibilityOverride`).
- **Fleet**: Vehicle/Trailer as audited; **no axles/loading meters/leasing detail/tachograph**; `EmissionClass` string-stored (`Euro3..Euro6, Electric, Other`) — additive enum values safe; `FleetDocument` metadata CRUD with expiry statuses but **no upload endpoints** (`DocumentPath` unreachable); `MaintenanceRecord`/`Inspection`/`MaintenancePolicy`/`DamageReport` (incl. `DowntimeDays`, `RepairCost`); `FuelTransaction` + computed consumption; fleet dashboard; KPI read models are vehicle-filterable (`KpiQueryService`, `ProfitabilityQueryService` dimension Vehicle).

## Architecture Decisions (locked)

1. **Legal entity = new `LegalEntity` in `Modules/Organization`** (`LegalEntity : AuditableTenantEntity`): `LegalName`, `TradingName?`, `CompanyNumber?`, `VatNumber?`, `PeppolId?`, `PeppolScheme?`, address block (`Street/HouseNumber/PostalCode/City/CountryCode`), `Email?`, `PhoneNumber?`, `Website?`, `Iban?`, `Bic?`, `BankName?`, `DefaultCurrency = "EUR"`, `PaymentTermDays = 30`, `InvoiceNumberFormat = "{YYYY}{MM}{SEQ}"`, `InvoiceSequencePadding = 4` (2–8), `InvoicePrefix?` (free text prepended by `{PREFIX}` token), `InvoiceFooter?`, `LogoStorageKey?` (real upload via `IFileStorageService`, category `legal-entities`), `IsActive`, `IsDefault` (exactly one per tenant via filtered unique index). Name choice: "LegalEntity" (DB `legal_entities`), UI Dutch: "Facturerende entiteit / Eigen bedrijven".
2. **Legal-entity bootstrap**: idempotent startup seeder (`LegalEntitySeeder`, invoked next to existing seeders) creates one default entity per tenant from `TenantSettings` company fields when none exists. `TenantSettings` invoice counters remain untouched for historic behavior but the invoice path switches to entity sequences (decision 4).
3. **Active-entity selection is user-scoped, cosmetic-not-authoritative**: new `UserLegalEntitySelection : AuditableTenantEntity` (`UserId`, `LegalEntityId`, unique `(TenantId, UserId)`), endpoints `GET/PUT api/me/active-legal-entity` (auth-only, like `MeController`). It only pre-fills pickers/defaults in the UI; every mutation still validates the explicit `LegalEntityId` server-side against tenant + active status — selection can never bypass tenant boundaries.
4. **Invoice numbering = per-entity, per-month sequence rows.** New `InvoiceSequence : AuditableTenantEntity` (`LegalEntityId`, `Year`, `Month`, `NextValue` **concurrency token**, unique `(TenantId, LegalEntityId, Year, Month)`). New `InvoiceNumberService`: `ComposeAsync(entity, period)` renders tokens `{YYYY} {YY} {MM} {SEQ} {PREFIX}` from `InvoiceNumberFormat`; claim loop mirrors `TenantNumbering` (reload row on `DbUpdateConcurrencyException`, ≤3 attempts, create-row race handled by unique index + retry). `Invoice` gains `LegalEntityId (Guid?)` (required for NEW invoices at service level; nullable column for historic rows), `InvoicePeriodYear/Month (int)` (defaults from `InvoiceDate`, user may pick an earlier month explicitly; future months rejected; changing period on a Draft re-issues a number and audits `PeriodChanged`), and `NumberIsManual (bool)`. Manual number correction: Draft-only, permission `invoices.override_number`, mandatory reason, uniqueness enforced, audited `NumberOverridden`. Preview endpoint `GET api/invoices/next-number?legalEntityId&year&month` returns the next expected number **without claiming**. Cancelled/deleted invoices never release numbers (counters only move forward).
5. **Invoice seller snapshot**: on creation (and refreshed on Draft edit) the invoice copies entity facts into new columns `SellerName`, `SellerVatNumber?`, `SellerIban?`, `SellerAddressLine?` (+ existing per-line VAT). Customer fiscal snapshot: `CustomerVatTreatment (string)`, `CustomerVatNumberSnapshot?`, `PurchaseOrderNumber?`. Sending (`Draft→Sent`) hard-validates: active same-tenant legal entity (Dutch error: "Deze factuur heeft geen geldige facturerende entiteit en kan niet worden verzonden."), PO policy (decision 9), VAT-number-required treatments. Later master-data changes never mutate Sent/Paid invoices.
6. **Customer import = clone of `PackageImportService` pattern**: `CustomerImportService` (`Modules/Partners/Services`) with `BuildTemplate()` ("Klanten" + "Uitleg" sheets), `PreviewAsync`, `CommitAsync(allOrNothing: true default, allowUpdates: false default)`; matches existing customers by `CustomerNumber`; validates number uniqueness (file-internal + DB), VAT via `VatNumberValidator`, country codes, reports exact row+value, error workbook; audited `Imported`. Permission `customers.import`. Manual create/edit accepts an explicit `CustomerNumber` (blocks duplicates with Dutch message); changing an existing number requires `customers.override_number` + reason, audited `NumberChanged`.
7. **Contacts + addresses extend what exists.** `CustomerContact` gains `DisplayName?`, `Nickname?`, `MobilePhone?`, `Department?` → new tenant lookup `ContactDepartment : LookupEntity` (`Modules/Partners`, seeded PLAN/BOEK/AANK/MAG/DIR/KLNT/CLAIM, FE `LookupSelect` with inline create, perms `contact_departments.view/manage`), `JobTitle?` (existing `Role` column kept as job title alias — new `JobTitle` NOT added; `Role` is relabeled "Functie" in UI), `PreferredLanguageCode?`, `IsActive = true`. Addresses stay `Location`-based: `LocationType` enum gains additive values `RegisteredOffice, AdministrativeAddress, BillingAddress, ReturnsAddress`; `Location` gains `IsDefaultBillingLocation` (filtered unique per customer, like existing loading/unloading defaults). Customer detail gets an address panel driven by existing Locations CRUD + quick-create; the inline Customer address block remains the "registered/primary" address (unchanged columns).
8. **Fiscal/bank/registry**: `Customer` gains `Nickname?`, `CurrencyCode = "EUR"`, `Iban?`, `Bic?`, `BankName?`, `BankAccountNumber?` (all optional; IBAN validated with the existing employee IBAN mod-97 validator moved to `Common/Validation/BankingValidators` and reused by both modules — move, don't duplicate). Company-registry seam: `ICompanyRegistryProvider` (`Modules/Partners/Services`, `Task<CompanyRegistryResult?> LookupAsync(string vatOrCompanyNumber, CancellationToken)`) + `NullCompanyRegistryProvider` returning provider-not-configured; endpoint `POST api/customers/registry-lookup` returns 200 `{ configured: false }` today; FE shows a manual "Opzoeken" button with a no-provider state and never overwrites fields without user confirmation. No scraping.
9. **VAT treatment stays the single enum + rate pair** (already coherent). We add a static `VatTreatmentCatalog` (`Modules/Partners`): per treatment → Dutch label, `RequiresVatNumber`, `AllowedRates` (`DomesticVat: [0,6,12,21]` + custom-with-permission), `DefaultRatePercent?`, `InvoiceLegalText?` (e.g. "BTW verlegd — art. 51 §2 W.BTW" for ReverseCharge, "Intracommunautaire levering — vrijgesteld art. 39bis W.BTW"). Backend validation on customer save uses the catalog; invoice creation copies effective treatment + legal text (decision 5). FE `CustomerForm` collapses "treatment + rate" into one coherent section (treatment select drives the rate control). Historical invoice VAT untouched.
10. **PO policy = enum + effective-dated history.** `Customer.PurchaseOrderPolicy` enum (`None|Optional|Required`, string-stored) backfilled from `PurchaseOrderRequired` (true→Required, false→None); the old bool stays and is kept in sync on write (deprecated, not dropped). New `CustomerPurchaseOrderNumber : AuditableTenantEntity` (`CustomerId`, `PoNumber`, `ValidFrom (DateOnly)`, `ValidUntil?`, `Notes?`) — history, never overwritten; "effective" = row covering a date, latest `ValidFrom` wins. Order keeps `CustomerReference` as its PO carrier (relabeled "Referentie / PO-nummer"); `Invoice.PurchaseOrderNumber` defaults from effective customer PO (by invoice period) else the referenced orders' distinct `CustomerReference` (single value only); manual invoice override requires `invoices.edit` (Draft) and is audited. `Draft→Sent` with policy Required and empty PO → blocked: "Deze klant vereist een PO-nummer. Voeg een geldig PO-nummer toe voor verzending." Permission `customers.manage_po` for policy + history mutations.
11. **Diesel surcharge = customer config + order override + invoice-time calculation strategy.** New `CustomerDieselSurcharge : AuditableTenantEntity` (`CustomerId` unique-active, `Enabled`, `Percent (decimal 5,2)`, `Basis` enum `CalculationBasis { OrderAmount, InvoiceSubtotal }` (string), `Presentation` enum `SurchargePresentation { PerOrderLine, AggregatedLine }`, `RoundingRule` enum `{ NearestCent, RoundUpCent }`, `FormulaDescription?`, `EffectiveFrom?`, `EffectiveUntil?`, `IsActive`). `TransportOrder` gains `DieselSurchargeOverride (bool)`, `DieselSurchargePercentOverride (decimal?)`, `DieselSurchargeOverrideReason?` (reason mandatory when overriding; inherited value + override + actor audited `DieselSurchargeOverridden`). New pure `DieselSurchargeCalculator` (strategy seam `IDieselSurchargeCalculator`): given config + orders → surcharge lines; invoice creation appends either one line per order ("Dieseltoeslag {pct}% — {orderNumber}") or one aggregated line; the base lines are never inflated (no double counting). Documented variables only (base price = order line amount, percentage); **no formula engine** — `FormulaDescription` is explanatory text; the customer's Excel formula maps later onto the strategy seam. Permission `customers.manage_surcharge`. Dossier scope: aggregation presentation covers dossier-level invoicing (orders of one dossier on one invoice → one aggregated line); no separate dossier config in this wave (documented limitation).
12. **Communication rules**: `CustomerCommunicationRule : AuditableTenantEntity` (`CustomerId`, `Type` enum `CustomerCommunicationType { PlanningAlert, DeliveryChange, DelayNotification, EtaUpdate, OrderConfirmation, Invoice, InvoiceReminder, GeneralReminder, Claims, Other }` string-stored, `CustomTypeLabel?`, `Channel = "Email"`, `CcEmail?`, `LanguageCode?`, `FallbackContactId?`, `IsActive`) + join `CustomerCommunicationRuleContact` (`RuleId`, `ContactId`) — real FK links to `CustomerContact`, no free-text names; effective address = contact email (rule-level `OverrideEmail?` allowed per linked contact? NO — keep simple: contact email is authoritative; rule-level `CcEmail` free).
